# Phase 3E Implementation — Approval-Only Multi-Agent Dashboard

**Status:** Complete

**Implemented:** 2026-07-27

**Blueprint reference:** [Phase 3E](20-PHASE-BLUEPRINT.md#phase-3-light-multi-agent-max-3-agents--controlled-introduction)

## Scope delivered

Phase 3E completes the controlled Phase 3 user interface without increasing autonomy. The Side Panel can now create and inspect a deterministic Planner → Coder → Critic plan, show per-role state and estimated cost, and approve tasks in the required order.

It still deliberately does **not**:

- launch browser tabs,
- invoke models,
- execute tools,
- navigate to arbitrary URLs,
- read arbitrary page DOM,
- persist full conversations, or
- mutate Arena content automatically.

## Worker-owned orchestration service

`src/background/orchestration-service.ts` now owns the active Phase 3E plan lifecycle in the MV3 worker. It wraps the deterministic orchestrator and dashboard projection with:

- default Phase 3 cost policy (`$0.50` workflow, `$0.30` per agent),
- hard cost reservations generated by the existing `CostGovernance` engine,
- replacement-plan reservation release to avoid stale approval-only reservations,
- approval calls routed through `OrchestrationDashboardState` before the safety guard is marked approved, and
- structured trace events for plan creation, task approval, status snapshots, and future lifecycle transitions.

The service exposes only approval/lifecycle state. It has no launcher method and no model/tool execution path.

## Explicit task transition rules

`OrchestrationDashboardState` now makes Phase 3E lifecycle rules explicit and tested:

1. **Planner before Coder approval:** `coder-1` cannot be approved until `planner-1` is approved or completed.
2. **Coder before Critic approval:** `critic-1` cannot be approved until `coder-1` is approved or completed.
3. **Execution dependency gate:** a task cannot enter `running` unless it has explicit human approval and all dependencies are `completed`.
4. **Status state machine:**
   - `pending → running | blocked`
   - `running → completed | failed | blocked`
   - `completed`, `failed`, and `blocked` are terminal.
5. **Invalid transitions fail closed** with `OrchestrationTransitionError`.

This preserves the approval-only UI while preparing a safe lifecycle contract for later manual execution work.

## Runtime message validation

The service worker now uses a strict `src/background/orchestration-messages.ts` validator for the only accepted orchestration messages:

| Message | Accepted shape | Notes |
|---|---|---|
| `aamp:orchestration:create` | `{ type, goal }` | Goal must be non-empty after trimming and ≤ 4,000 characters. Unknown fields are rejected. |
| `aamp:orchestration:approve` | `{ type, taskId }` | Task ID must match the Phase 3 role-task pattern, e.g. `planner-1`. Unknown fields are rejected. |
| `aamp:orchestration:status` | `{ type }` | No payload fields are accepted. |

Messages are still accepted only from extension-owned senders. Malformed orchestration messages are ignored by the worker dispatcher; well-formed but lifecycle-invalid requests return a bounded `{ ok: false, error }` response.

## Side Panel rendering

The orchestration rendering path was extracted to `src/sidepanel/orchestration-dashboard.ts` so it can be unit-tested independently from the Side Panel boot code. The renderer:

- validates bounded worker responses before rendering,
- uses `textContent` and DOM node creation only,
- uses explicit task IDs supplied by the worker instead of reconstructing IDs from labels,
- disables approval buttons for dependency-blocked tasks, and
- renders inactive plans as a safe text-only state.

The Side Panel safety copy now clarifies that automatic agent launch, model execution, and tool execution remain disabled.

## Observability

Phase 3E adds structured trace events through the existing bounded `Tracer`:

- `orchestration.plan.created`
- `orchestration.task.approved`
- `orchestration.task.statusChanged`
- `orchestration.status.snapshot`

Every trace event receives the tracer's correlation ID and sanitized primitive attributes. No prompt bodies, DOM text, file contents, or conversation history are added to trace attributes.
